#+description: Core-only StarIntel face extraction, durable similarity gallery and explicitly reviewed candidate graph.

* Working Foundation

face-intel is a standalone Person data actor service. Pykka actors own supplied
Person records, photo ingestion, core candidate Person records, explicit image-to-Person Relations,
exact normalized name/alias search, and canonical Target dispatch. CouchDB stores
canonical documents and original images. The service owns its HTTP interface.

The optional YuNet/SFace pipeline extracts faces and proposes candidate links
as images arrive. Confirmation is an explicit review by another actor or a human.
It does not infer names, gender, or other identity attributes from images. Later Person data modules have a separate roadmap
in =roam/indexes/person-data-roadmap.org=.

* Run

Python 3.12+, uv, and CouchDB 3.x are required. Docker Compose is optional.

#+begin_src sh
uv sync --frozen --extra dev
export FACE_INTEL_API_TOKEN="$(uv run --frozen python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
read -r -p 'CouchDB username: ' COUCHDB_USERNAME
read -rs -p 'CouchDB password: ' COUCHDB_PASSWORD
export COUCHDB_USERNAME COUCHDB_PASSWORD
# Optional: start a new local CouchDB using the supplied Compose file.
docker compose up -d
uv run --frozen face-intel
#+end_src

The default service address is =http://127.0.0.1:8088=. Configure an existing CouchDB
with =COUCHDB_URL= and =COUCHDB_DATABASE=. =FACE_INTEL_DATASET= defaults to
=face-intel=. Credentials and the API token are read from environment variables;
no credential file is included. Keep the token in the same shell for API clients.
The Compose volume persists CouchDB data across container restarts.

An externally exposed service can be started through a reverse proxy or with:

#+begin_src sh
uv run --frozen uvicorn face_intel.api:create_app --factory --host 0.0.0.0 --port 8088
#+end_src

The database user must be able to create the database and maintain its
=_design/face-intel= views. Deploying a live instance is separate from this PR.

* Local Star Language Pin

=src/face_intel/contracts/= contains unmodified generated Star Language 0.10.1
schema and Python types, =core.star=, and the upstream release lock from commit
=e9ec1d883627d186aafe0b3647bdc29baea03543=. =pin.json= records source and file hashes.
Startup and =scripts/check-spec.py= verify the dependency against the upstream
release lock. This core pin is from upstream main.

Public objects use =id=, =schemaVersion=, lowerCamelCase fields, and typed
=StarReference= objects. =Photo= in this service maps to the canonical =Picture=
type. CouchDB =_id=, =_rev=, and =_attachments= are handled only in the store adapter;
the public current revision is =rev=. Generated files must not be edited.
See =THIRD_PARTY.md= for upstream attribution and retained license.

* Core-Only Image Claims

Only =org.starintel/core@1= version =0.10.1= is consumed. There is no FaceIntel
schema library or custom document dtype. A tentative person is a core =Person=
with =verificationStatus: candidate=. Its identity can later be confirmed through
a revision-checked Person update without changing its ID or type.

An image association is a core =Relation= whose =source= references a =Picture=,
=destination= references a =Person=, and =predicate= is the core
=org.starintel/core@1/related-to=. Candidate status belongs to the Relation's
=verificationStatus=; =provenance.basis= records the supplied claim evidence.
The service accepts =candidate=, =confirmed=, and =rejected= for these image
associations. These are application rules on the core string field.

=POST /v1/links/photo-person= creates an idempotent candidate Relation. To confirm
or reject it, =POST /v1/relations= with the returned document, its current =rev=,
updated =verificationStatus=, a nonempty =evidence= reference list,
=provenance.basis=, =verifiedBy= reviewer, and integer Unix =verifiedAt= review time. An actual edit without =rev= or
with a stale =rev= fails with 409; an identical retry remains idempotent. The
Person and Relation are separate claims: confirming one does not confirm the
other. =extensions.faceIntel.candidate= and =status= are derived convenience
metadata refreshed from =verificationStatus=, not additional schema fields.
CouchDB revisions provide conflict detection, not a permanent review-history log.

A full-image claim uses the Picture directly. A face-region claim can include
=extensions.faceIntel.region= with integer =x=, =y=, =width=, and =height= on the
Relation; the rectangle must fit the source Picture's stored pixels. This uses
core's open metadata map. A cropped face is another core Picture. Its provenance
can use a core =derived-from= Relation to the original Picture; the inherited
core File fields also provide =parentFile= and =derivedFiles=.

Core 0.10.1 defines =File=, =Image= extending File, and =Picture= extending Image.
HTTP photo upload handles Pictures. The Rabbit worker also imports core Files
and Images whose bytes are images, retaining the source document and deriving
a core Picture with =parentFile=. Relation endpoints accept locally stored
Persons, Pictures, Images and Files. StarIntel Server supplies binary ingress
=POST /api/v1/files= and download =GET /api/v1/files/<id>/content=; metadata
continues through its generic document APIs.

The former =face-observation=, =candidate-person=, and =face-person-candidate=
dtypes and their HTTP/Target operations have been removed. Existing custom-type
records are not automatically rewritten. Earlier exports must be explicitly
converted to core Persons, Pictures, and Relations before reingestion; changing
only dtype would leave invalid custom fields. Legacy annotation predicates also
need explicit conversion to core =related-to=. No live database was migrated.

* HTTP Interface

All =/v1/= endpoints require =Authorization: Bearer <token>=. =/health= exposes
service liveness only. Production always uses CouchDB; memory stores exist only
as explicitly injected test fixtures.

| Method | Path | Input or result |
|--------+------+-----------------|
| GET | /health | Actor liveness and contract version |
| GET | /v1/manifest | Canonical public ActorManifest |
| POST | /v1/persons | Canonical supplied Person document |
| GET | /v1/search/name?q=... | Exact normalized name/alias page |
| GET | /v1/persons/<id> | Person plus linked Pictures and Relations |
| POST | /v1/photos | Raw PNG, JPEG, or WebP bytes |
| GET | /v1/photos/<id> | Canonical Picture metadata |
| GET | /v1/photo-bytes/<id> | Original image bytes |
| POST | /v1/links/photo-person | photoId, personId, basis |
| POST | /v1/targets | Canonical Target; same actor operations |
| POST | /v1/images/process | photoId, optional minScore and limit |
| POST | /v1/faces/register | aligned photoId, personId, basis |
| POST | /v1/search/face-similarity | queryPhotoId, candidatePhotoIds, limit |
| POST | /v1/relations | Create or revision-check an update to a core Relation |
| GET | /v1/relations/<id> | Core Relation |

Search normalizes Unicode with NFKC and casefold, then collapses whitespace. It
matches complete names or aliases; this is not fuzzy text or biometric search.
Equal names on different document IDs remain distinct Persons. Unnamed supplied
Person documents are supported and simply have no name index keys.

* Person and Photo Example

#+begin_src python
import os
from pathlib import Path
import httpx

headers = {"Authorization": "Bearer " + os.environ["FACE_INTEL_API_TOKEN"]}
with httpx.Client(base_url="http://127.0.0.1:8088", headers=headers) as client:
    record = client.post("/v1/persons", json={
        "id": "person:example", "dataset": "face-intel", "dtype": "person",
        "schemaVersion": "0.10.1", "fullName": "Example Person",
        "aliases": ["Example Alias"],
    })
    record.raise_for_status()
    picture = client.post("/v1/photos", content=Path("photo.png").read_bytes())
    picture.raise_for_status()
    annotation = client.post("/v1/links/photo-person", json={
        "photoId": picture.json()["id"], "personId": record.json()["id"],
        "basis": "Explicit annotation supplied with these records",
    })
    annotation.raise_for_status()
#+end_src

Supplied canonical Person fields and provenance are preserved. The reserved
=extensions.faceIntel.nameKeys= projection is regenerated from supplied names
and aliases. An annotation never identifies a face, merges people, or changes
Person identity fields. Its Relation keeps =verificationStatus: candidate= and
=extensions.faceIntel.candidate: true=.

* Target Interface

Targets address =actor: face-intel=. =options= is a JSON object. Operations:

| Operation | target | Additional options | Output documents |
|-----------+--------+--------------------+------------------|
| process-image | Picture ID | minScore, limit | Original, crops, derivations, Persons and candidate Relations |
| register-face | Aligned Picture ID | personId, basis | Picture, Person and candidate Relation |
| search-similar-faces | Aligned Picture ID | candidatePhotoIds, limit | Similarity metadata |
| search-name | Name or alias | limit, after | Person page |
| get-person | Person ID | limit, after | Person, Picture, Relation page |
| get-photo | Picture ID | None | Picture |
| ingest-relation | Relation ID | document with matching id | Relation |
| get-relation | Relation ID | None | Relation |
| ingest-person | Person ID | document with matching id | Person |
| ingest-photo | Content hash Picture ID | photoBase64 | Picture |
| link-photo-person | Picture ID | personId, basis | Person, Picture, Relation |

#+begin_src json
{
  "id": "target:example", "dataset": "face-intel", "dtype": "target",
  "schemaVersion": "0.10.1", "actor": "face-intel", "target": "person:example",
  "options": {"operation": "get-person", "limit": 20}
}
#+end_src

The response contains =target=, =documents=, and =nextCursor=. The returned Target
has state completed and typed references in =extensions.faceIntel.resultRefs=.
It is a synchronous dispatch result; Target execution status is not persisted,
leased, scheduled, or consumed from a broker by this slice. Scheduling fields
are the responsibility of the caller's scheduler. Large photos should use raw
HTTP upload; Target JSON bodies are capped at 1 MiB including base64 encoding.

* Facial Similarity of Supplied Crops

The optional similarity engine consumes stored Pictures containing single,
already aligned 112x112 face crops. The crop producer must perform detection,
landmark alignment, and EXIF normalization before uploading through =POST
/v1/photos=. Resizing a bounding box alone does not establish SFace alignment.
This supplied-list endpoint is read-only. The incoming-image pipeline below
performs detection, alignment, and a bounded durable gallery search.

Install =uv sync --frozen --extra similarity= and configure both
=FACE_INTEL_SFACE_MODEL= (local ONNX path) and =FACE_INTEL_SFACE_SHA256= (lowercase
SHA-256 digest). Startup loads the verified model bytes in a dedicated bounded
actor. Missing configuration leaves the foundation available and similarity
unadvertised; invalid model configuration fails startup. No model download occurs
at runtime. The manifest advertises =face.similarity.search= and the model ID,
cosine metric, and crop dimensions only when enabled.

The initial backend is the float32 OpenCV Zoo SFace model:
- Source commit: =47534e27c9851bb1128ccc0102f1145e27f23f98=.
- File: =models/face_recognition_sface/face_recognition_sface_2021dec.onnx=.
- SHA-256: =0ba9fbfa01b5270c96627c4ef784da859931e02f04419c829e83484087c34e79=.
- Download: [[https://media.githubusercontent.com/media/opencv/opencv_zoo/47534e27c9851bb1128ccc0102f1145e27f23f98/models/face_recognition_sface/face_recognition_sface_2021dec.onnx][Pinned OpenCV Zoo model]]. Keep downloaded model files outside the repository.

Send an authenticated =POST /v1/search/face-similarity=:

#+begin_src json
{
  "queryPhotoId": "picture:sha256:<query-crop-hash>",
  "candidatePhotoIds": ["picture:sha256:<candidate-crop-hash>"],
  "limit": 20
}
#+end_src

One candidate gives a pairwise comparison. Up to 100 distinct candidate IDs are
allowed; limit is 1-100 (default 20). The query may also appear in the candidate
list; each distinct ID is embedded once per request. Results contain =query=,
=modelId= (including the exact model hash), =metric: cosine=, =candidateCount=,
and ranked =matches= with typed =picture= references and =score=. Scores range
from -1 to 1; ties sort by Picture ID. Results reflect the supplied list, not a
global nearest-neighbor index. Any missing, malformed, or unaligned-size crop
fails the entire request. No partial ranking is returned.

Cosine scores are not probabilities or identity confirmation. No default identity
threshold is applied. The engine does not modify Persons, candidate annotations,
or relations. The separate pipeline persists model-specific vectors on crop
Pictures in core =extensions= metadata; restrict database and API access accordingly. Model changes produce
different model IDs and require separate calibration on representative data.

The same operation runs via =POST /v1/targets=: set =target= to the query Picture
ID and =options= to =operation: search-similar-faces=, =candidatePhotoIds=, and
optional =limit=. The completed Target contains the result in
=extensions.faceIntel.similarity=; =documents= and =resultRefs= are empty because
this read-only operation creates no canonical documents.

For real inference validation, set =FACE_INTEL_TEST_SFACE_MODEL= and
=FACE_INTEL_TEST_SFACE_SHA256= to the pinned model, then run:

#+begin_src sh
uv run --frozen --extra dev --extra similarity python3 -m unittest discover -s tests -p 'test_similarity.py' -v
#+end_src

That smoke test compares 128-dimensional output against OpenCV FaceRecognizerSF
for a deterministic color/spatial fixture. It checks inference and preprocessing,
not recognition accuracy. Without a model it is explicitly skipped. The actor
checks deadlines between reads and inference calls; an already-running native
inference cannot be interrupted, but expired work starts no further model calls.

* Incoming Images and Candidate Lifecycle

Install =uv sync --frozen --extra similarity --extra broker=. Configure the SFace
model above plus =FACE_INTEL_YUNET_MODEL= and =FACE_INTEL_YUNET_SHA256=:
- Detector: OpenCV Zoo commit =47534e27c9851bb1128ccc0102f1145e27f23f98=,
  =models/face_detection_yunet/face_detection_yunet_2023mar.onnx=.
- SHA-256: =8f2383e4dd3cfbb4553ea8718107fc0423210dc964f9f4280604804ed2552fa4=.
- [[https://media.githubusercontent.com/media/opencv/opencv_zoo/47534e27c9851bb1128ccc0102f1145e27f23f98/models/face_detection_yunet/face_detection_yunet_2023mar.onnx][Pinned YuNet model]], verified before loading; no runtime download.

=POST /v1/images/process= with ={"photoId": "picture:..."}= detects faces,
aligns 112x112 crops using five landmarks, and embeds them with SFace. Crops are
core Pictures with model-specific vectors, detector provenance and a core
=derived-from= Relation to the original. A matching gallery crop can suggest
its linked Person; otherwise the pipeline creates an unnamed candidate core
Person. Each suggested crop-to-Person Relation remains =candidate=, including
suggestions involving an already confirmed Person. Multiple plausible Persons
remain separate claims; the service does not merge them.

=POST /v1/faces/register= associates an existing aligned 112x112 crop with a
supplied Person for gallery matching. It requires =photoId=, =personId= and
=basis= and creates a candidate link. Review that link explicitly when warranted.
The gallery includes candidate and confirmed links, skips rejected claims and
rejected Persons, and partitions vectors by model ID and dataset.

The processing =minScore= defaults to 0.5 (allowed -1 through 1) and =limit= to
5 (allowed 1 through 20). This is an operating cutoff for suggestions, not a
calibrated identity threshold. Detection is bounded to 32 faces per image and
search to 1,000 gallery crops by default. =galleryTruncated= reports when the
bounded gallery omits crops. Detection downsizes large images for inference.
Inputs must already have EXIF orientation normalized and contain a single frame.
Repeated matches never promote a Person or Relation to confirmed automatically.
Other actors submit explicit review updates with evidence, reviewer and timestamp;
Person identity and each image association can be reviewed independently.

Set =FACE_INTEL_AUTO_PROCESS_IMAGES=1 to process after HTTP image upload. The
original bytes are committed first. On a processing failure, retry processing
using the returned/deterministic Picture ID. Processing writes a deterministic
core Target completion ledger after graph writes; completed runs replay current
records, preserving later reviews, across restarts. Partial writes recover using
deterministic IDs. The graph is multiple CouchDB writes, so an interrupted run
may leave partial records and retries can observe a changed gallery.

For continuous StarIntel Server delivery, configure =STARINTEL_SERVER_URL=,
=STARINTEL_SERVER_TOKEN=, =FACE_INTEL_RABBIT_URL= and optionally
=FACE_INTEL_RABBIT_QUEUE= (default =face-intel.images=), then run:

#+begin_src sh
uv run --frozen --extra similarity --extra broker face-intel-worker
#+end_src

The worker consumes committed =documents.new.picture=, =documents.new.image=
and =documents.new.file= events, plus their =documents.updated.*= counterparts
for metadata-first attachment delivery, on the durable =documents= topic exchange.
It fetches current canonical metadata and bytes from the server, checks SHA-256
and size, stores the source locally, processes it, and exports graph records and
crop bytes back to the server. Server binary uploads are capped at 8 MiB;
use that lower limit for incoming server files. Generated crops are skipped to
prevent recursion. Non-image Files are outside the worker's capability.

Acknowledgment happens after local persistence and remote document visibility.
Temporary failures requeue; invalid input goes to the owned queue's =.dead=
queue/exchange. Run under a supervisor to restart after broker disconnection.
The worker also consumes =documents.updated.person= and
=documents.updated.relation= to mirror reviews of its local graph. It fetches
latest state to handle stale events; replay/export does not overwrite remote
reviews. It does not subscribe to server Target dispatch because that transport
currently lacks a canonical remote completion protocol; local HTTP and core
Target operations are supported.

Real model tests opt in with =FACE_INTEL_TEST_YUNET_MODEL=,
=FACE_INTEL_TEST_YUNET_SHA256=, the SFace test variables above and
=FACE_INTEL_TEST_FACE_IMAGE=. CI fetches a hash-checked OpenCV fixture outside the
repository. These checks prove inference, alignment and graph generation;
recognition accuracy and thresholds need evaluation on representative data.

* Reliability and Limits

- Person creation and identical retries are idempotent. To edit a Person,
  include its current =rev=. Stale revisions fail with HTTP 409.
- Picture IDs are SHA-256 content hashes. The original attachment and metadata
  are committed in the same CouchDB write. Identical photo retries are deduplicated.
- An annotation ID derives from dataset, Picture, Person, and annotation basis.
  Repeating the same annotation yields the same candidate Relation.
- Name and annotation views are derived, dataset-scoped CouchDB indexes. Their
  deterministic design source is installed idempotently; unrelated views survive.
- Pages default to 20 and are capped at 100. Use returned =nextCursor= as =after=.
  Person bundle pagination applies to Relations. Pictures are deduplicated per page.
  View pages are not a snapshot across concurrent writes or replication.
- Photos are capped at 10 MiB and 20 million pixels. Only PNG/JPEG/WebP is accepted.
- Every actor mailbox is capped at 64 commands; admission waits at most 250 ms.
  Public calls use a 30-second propagated deadline; CouchDB calls time out in 5 seconds.
- Expired queued commands do not start new work. A network timeout during an active
  write can still leave a committed document; retry the same ID/revision and inspect
  the durable result. A client timeout is not proof that a write was rolled back.
- Invalid input is 422, missing records 404, oversized bodies 413, and unavailable
  actors/store or elapsed deadlines 503. Tokens, CouchDB credentials, and raw backend
  error messages are not returned.

* Actor Ownership

=TargetActor= routes to =PersonActor=, =PhotoActor=, =SimilarityActor= and =PipelineActor=. Those actors send immutable
command envelopes to =StoreActor=, which owns CouchDB state and its HTTP client.
SimilarityActor owns optional supplied-crop inference; PipelineActor owns detection,
alignment and durable gallery processing. Caller mappings are copied before mailbox transfer. Actors stop in reverse dependency
order and startup failures clean up only this system's actor references.

To add a Person module, retain canonical generated documents and typed references,
add bounded commands to a focused actor, route both HTTP and Target transports to
that actor, advertise only implemented capabilities, and add regression evidence.
Do not expose data-specific operations in generic StarIntel ingest by default.
